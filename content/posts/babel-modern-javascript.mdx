For a long stretch of JavaScript history, choosing new syntax meant choosing which users you were willing to leave behind. Babel changed that calculation.

You could write an arrow function, a class, or destructuring assignment while an older browser still had no idea what any of it meant. The build translated the syntax while your source and the web kept moving.

[Sebastian McKenzie](https://github.com/sebmck) ([LinkedIn](https://www.linkedin.com/in/sebastian-mckenzie-96925b106), [X](https://x.com/sebmck)) started the project as 6to5. [Jamie Kyle](https://github.com/jamiebuilds) ([LinkedIn](https://www.linkedin.com/in/jamiebuilds)) helped turn the transpiler into a platform. The [Babel community](https://babeljs.io/team), along with the people behind the compilers, parsers, transforms, and polyfills it built upon, carried the idea much farther.

This is the third post in *The Web We Inherited*, a series about the tools and people whose work became part of the platform beneath us. The first two looked at [jQuery](/posts/jquery-compatibility-layer-shaped-web), which gave developers one vocabulary for inconsistent browsers, and [ESLint](/posts/eslint-making-javascript-rules-programmable), which turned code review into a programmable platform. Babel changed which JavaScript you were allowed to write in the first place. I usually experienced it indirectly: it sat inside another tool and quietly made newer JavaScript safe to ship, hiding the interesting part, where compatibility data, extension points, careful semantics, and years of maintenance did as much work as the compiler itself.

## What Babel changes before JavaScript runs

Think of Babel as a translator between editions of JavaScript. You write newer syntax, and with target-aware configuration such as `preset-env`, Babel uses declared environments and compatibility data to rewrite the parts older engines may not understand, when a faithful transformation is possible. That covers syntax; newer APIs such as `Promise` need separately configured polyfills when a target lacks them.

The rewrite is not mechanical. Real transformations must preserve semantics a short before/after would hide, so Babel sometimes emits helpers, and its [compiler assumptions](https://babeljs.io/docs/assumptions) can produce smaller output at the cost of behavior when those assumptions do not hold. In most systems this happens during the build: browsers and servers still execute plain JavaScript, and Babel lets developers author newer syntax without requiring every runtime to understand it on the same day.

## Before 6to5

Babel belonged to a lineage. [CoffeeScript](https://coffeescript.org/v1/#changelog) (2009) normalized compile-to-JavaScript for a generation of web developers. Google's [Traceur](https://github.com/google/traceur-compiler) translated "JavaScript.next" so developers could test proposals, [TypeScript](https://devblogs.microsoft.com/typescript/ten-years-of-typescript/) (2012) emitted JavaScript while adding static types, and Facebook's [JSTransform](https://github.com/facebookarchive/jstransform) offered pluggable transforms for JSX and parts of ES6. Projects like esnext explored the same ground.

They also supplied foundations. [Babel's first package](https://github.com/babel/babel/blob/c97696c224d718d96848df9e1577f337b45464be/package.json) parsed with the esnext fork of [Ariya Hidayat](https://github.com/ariya)'s Esprima and walked and printed trees with [Yusuke Suzuki](https://github.com/Constellation)'s Estraverse and Escodegen; today's [`@babel/parser`](https://babeljs.io/docs/babel-parser) credits Acorn's [Marijn Haverbeke](https://github.com/marijnh). The homage belongs to these road builders too.

McKenzie's [first public commit](https://github.com/babel/babel/commit/c97696c224d718d96848df9e1577f337b45464be) landed on September 28, 2014, and the [original README](https://github.com/babel/babel/blob/c97696c224d718d96848df9e1577f337b45464be/README.md) promised: "6to5 turns ES6 code into vanilla ES5, so you can use ES6 features today." It began as an educational project that McKenzie [started to understand compilers](https://podcast.babeljs.io/rome/), and [Sindre Sorhus](https://github.com/sindresorhus) built the early Grunt and Gulp integrations that turned it into usable infrastructure.

In January 2015, 6to5 and esnext chose to combine rather than compete. [Stefan Penner](https://github.com/stefanpenner) started the conversation, with [Rich Harris](https://github.com/Rich-Harris) among the esnext participants; the teams ported esnext's tests and pointed its users to 6to5. That month 6to5 reported [100,000 npm downloads and integrations with every major JavaScript build system](https://babeljs.io/blog/2015/01/12/6to5-esnext). That was package activity, not a count of people.

On February 15, [6to5 became Babel](https://babeljs.io/blog/2015/02/15/not-born-to-die): the old name described one conversion, the new mission was a reusable JavaScript transformation platform. The announcement pointed to [ESTree](https://github.com/estree/estree), part of a broader shift toward shared syntax-tree conventions that reduced duplicated parser and traversal work across tools.

## What Babel rewrites, and what it can't

Babel is commonly called a transpiler: a compiler whose input and output are source code. Its durable architecture has three stages, parse then transform then generate. The parser turns source into a nested data structure, the abstract syntax tree (AST): an arrow becomes an `ArrowFunctionExpression` node a transform can visit, reason about, and replace. The generator prints the result, and a source map connects generated locations back to the original code.

This is not search and replace. In `setInterval(() => this.value++, 1000)`, changing the arrow to a `function` would alter how `this` is chosen, so a correct transform preserves that surrounding value, often by saving it in a variable. Classes and modules add more constraints, including `super`, live bindings, and initialization order, and lowering ESM to CommonJS cannot erase every semantic difference between the two systems.

[Kyle's Babel Plugin Handbook](https://github.com/jamiebuilds/babel-handbook/blob/master/translations/en/plugin-handbook.md) gave authors a vocabulary for this work: nodes, paths, visitors, scopes, and bindings. A plugin declares which nodes it wants to visit; Babel supplies traversal, scope analysis, generation, and source maps, applying plugins in configuration-sensitive order. That API made compiler extension approachable without pretending the semantics were simple.

It also helps define Babel's boundaries. Babel can rewrite module syntax, but resolving modules and building the dependency graph is a bundler's job. [Working with the TypeScript team](https://babeljs.io/blog/2018/08/27/7.0.0/), Babel 7 added a preset that [strips TypeScript annotations](https://babeljs.io/docs/#type-annotations-flow-and-typescript), but Babel does not type-check; `tsc` does that analysis.

Syntax and runtime APIs are separate too. An arrow is syntax; `Promise` and `Array.from` are APIs. A transform rewrites code an old engine cannot parse; a polyfill supplies an API it lacks. Helpers are a third category, the transform-generated machinery for things like classes, which Babel can inline or [`transform-runtime`](https://babeljs.io/docs/babel-plugin-transform-runtime) can pull from `@babel/runtime` (not itself a general polyfill).

That distinction illuminates work often experienced under Babel's name. [Ben Newman's Regenerator](https://facebook.github.io/regenerator/) turned generator functions into resumable state machines, and [Denis Pushkarev](https://github.com/zloirock)'s core-js supplied specification-oriented implementations of the standard library. His [project history](https://github.com/zloirock/core-js/blob/master/docs/2023-02-14-so-whats-next.md) records core-js entering 6to5 soon after its November 2014 release, shipped first as `6to5/polyfill` and later through `babel-polyfill`.

Babel branding could hide that: much of the library implementation was core-js, and some semantics never backport exactly. Babel's [caveats](https://babeljs.io/docs/caveats/) note that ES5 cannot properly subclass built-ins like `Array`. The honest promise was never "every new thing works everywhere," but that a large, useful part of the language could be translated while supporting pieces handled the rest.

## From compiler to shared platform

[Babel 5](https://babeljs.io/blog/2015/03/31/5.0.0/) (March 2015) added a public plugin API, `.babelrc`, and alignment with TC39's process, so developers could add transforms without forking the compiler and proposal implementers could make proposed syntax executable before browsers shipped it. [Babel 6](https://babeljs.io/blog/2015/10/29/6.0.0/) completed the shift: every transform became a plugin, internals shipped as packages, and default behavior moved into presets, which were shareable plugin configurations rather than separate compiler modes.

The migration was disruptive. Package relationships confused users, and many tiny modules multiplied installation and versioning problems; McKenzie extracted Babel's monorepo publishing machinery into what became [Lerna](https://github.com/lerna/lerna). Corporate support mattered (McKenzie worked on Babel 6 at Facebook), but the community would carry the platform after that push.

React gave teams a compelling reason to put such a compiler in frontend build pipelines: JSX. Babel offered one pipeline for JSX and new JavaScript syntax, and a February 2015 guide showed developers swapping `reactify`, `node-jsx`, and `jsx-loader` for [Babel integrations across Browserify, Node, Webpack, and Gulp](https://babeljs.io/blog/2015/02/23/babel-loves-react/).

## Targets, proposals, and the cost of convenience

The name 6to5 assumed a fixed destination: ES5. Browsers kept moving, so in 2016 `babel-preset-env` reframed the question from "which edition should I compile?" to "which environments do my users run?", combining target queries, compatibility data, and feature-to-transform mappings in an [Autoprefixer-like model](https://babeljs.io/blog/2016/12/07/the-state-of-babel).

When its compatibility tables mark every configured target as supporting a feature, `preset-env` omits that transform, and bugfix transforms cover known partial implementations. The result is smaller output, more native semantics, and a gradual path off old code; later `useBuiltIns` modes coordinated selective core-js imports, and Babel 8 moved polyfill injection into dedicated packages.

This was collaborative work: [Henry Zhu](https://github.com/hzoo) created the original preset repository, and contributors wired in browser data from [Juriy Zaytsev's compat-table](https://github.com/compat-table/compat-table) and queries from [Andrey Sitnik's Browserslist](https://github.com/browserslist/browserslist). Browser teams, polyfill maintainers, and bug reports supplied still more data beneath the friendly interface.

Ease also created risk. TC39 uses a staged process, and Babel let developers test proposal snapshots before broad native support. Specification review, conformance tests, and independent engines still decided what belonged in the language. Stage presets nevertheless blurred "available in a compiler" with "destined for JavaScript." Stage 0 was the pre-maturity strawperson category rather than a committee commitment, yet `stage-0` spread through boilerplates and production applications before semantics stabilized.

The team later said this worked ["maybe too well"](https://babeljs.io/blog/2018/07/27/removing-babels-stage-presets). Proposals changed or stalled, leaving incompatible transforms and migrations. Babel 7 stopped publishing official Stage presets and required explicit proposal-plugin opt-ins. The change kept experimentation while making the interface more honest about its risks.

For proposals whose designs diverged, most visibly the pipeline operator and [decorators](https://babeljs.io/blog/2018/09/17/decorators), Babel required configuration naming a proposal variant while keeping a labeled legacy mode. TC39 decided JavaScript; Babel made proposal snapshots executable and learned to label uncertainty more honestly.

## Stewardship after the breakthrough

After Babel 6, McKenzie and Kyle described burning out and shifted their attention elsewhere, while proposal changes, parser bugs, releases, and documentation remained and millions of downstream builds stood ready to reveal any regression.

Zhu's [2016 account](https://babeljs.io/blog/2016/12/07/the-state-of-babel) credits [Logan Smyth](https://github.com/loganfsmyth), [Daniel Tschinder](https://github.com/danez), [Brian Ng](https://github.com/existentialism), and others with taking on that work: consolidating the parser and preset-env repositories into the monorepo, carrying deep compiler and configuration work, and combining maintenance with communication, fundraising, and standards participation.

[Babel 7 shipped in 2018](https://babeljs.io/blog/2018/08/27/7.0.0/) after a long development cycle. It consolidated those lessons behind the `@babel` package scope and a more durable configuration contract.

The burden never vanished. In 2021 the team asked why infrastructure used by millions was [running out of money](https://babeljs.io/blog/2021/05/10/funding-update.html). Babel is often configured once and forgotten until it breaks, and that ubiquity hides the people who kept doing unglamorous work long after the novelty faded.

esbuild, SWC, and Oxc later pursued overlapping work with different performance tradeoffs. Their existence is not a verdict against Babel: it made target-aware compilation ordinary enough to optimize and rebuild, and its plugins remain a compatibility surface newer tools must consider.

## Babel 8 and the people who carried it

On June 16, 2026, the team [released Babel 8](https://babeljs.io/blog/2026/06/16/8.0.0/), eight years after Babel 7 and with no new language feature. Instead Babel became ESM-only, shipped TypeScript types, and made `preset-env` stop defaulting to ES5 and CommonJS, with Browserslist's moving `defaults` query as the baseline. Older output remains available on request, and although Babel 8 itself requires Node.js 22 or newer, the JavaScript it emits can still target older environments.

That is a fitting destination for a project born as 6to5: a compiler once built to translate ES6 into 2009-era JavaScript now generally avoids lowering tracked syntax when its configured targets support it. The announcement reported growth from 1.7 million weekly downloads in 2018 to 651 million in June 2026, a package metric inflated by automation but still a signal of how much now depends on Babel.

The announcement specifically names [Huáng Jùnliàng](https://github.com/JLHwung) ([X](https://x.com/JLHwung)), [liuxingbaoyu](https://github.com/liuxingbaoyu), and [Nicolò Ribaudo](https://github.com/nicolo-ribaudo) ([LinkedIn](https://it.linkedin.com/in/nicol%C3%B2-ribaudo-bb94b4187), [X](https://x.com/NicoloRibaudo)) as the core team behind the release. It also credits the Sovereign Tech Agency's financial support and Igalia's engineering time with making Babel 8 possible. The team inherited a decade of compatibility expectations and moved the compiler forward without treating disruption as ambition. That restraint is engineering too.

## What Babel taught me about compatibility

SDKs need an explicit compatibility contract. Babel made target choice visible and turned a huge matrix of runtimes into a repeatable build decision. An SDK can do the same with API versions, runtime support, generated types, and feature availability, then explain exactly which behavior it selected.

Babel's Stage presets also make me wary of frictionless experiments. Preview features need a name, pinned semantics, and a migration path before examples spread into production, and the core has to stay honest about which guarantees belong to the platform and which come from a plugin.

TC39 evolves ECMAScript through consensus and runtime teams implement it; earlier compilers had already shown source transformation could bridge the gap. Babel's contribution was to shorten the distance between an idea and production for the features it could faithfully lower, giving frameworks a shared transformation layer and letting applications target the runtimes they supported without freezing their source at the oldest one.

McKenzie began the experiment, and Kyle and the early team saw a platform inside it. Newman and Pushkarev built runtime and standard-library machinery that many Babel users never saw. Zhu, Smyth, Tschinder, Ng, Ribaudo, Huáng, liuxingbaoyu, and many others kept the compiler moving through migrations, specification changes, funding problems, and the long years after the launch excitement wore off.

Today, "write modern JavaScript and compile only what your supported targets need" sounds like an obvious build strategy. I see the work behind it whenever `preset-env` removes a transform because the configured targets finally support the feature in production.
